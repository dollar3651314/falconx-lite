## 1. 需要 Amos 审核的决定
| 编号 | 决定 | 我的建议 | 为什么 |
|---|---|---|---|
| W1 | 热钱包私钥放哪里 | 按已审核的架构方案（K-05）：**Amos 把私钥填进服务器环境变量**（`FX_WALLET_ETH_HOT_KEY` 给 ERC20 和 BSC 共用、`FX_WALLET_TRON_HOT_KEY`），同时填对应的公开地址（`FX_WALLET_ETH_HOT_ADDRESS`、`FX_WALLET_TRON_HOT_ADDRESS`）。启动时用私钥算出地址和填的地址对一遍，对不上就不启动提现、健康检查报错。私钥只在签名时用，不写日志、不出现在任何接口和错误信息里 | 密钥不经过 AI、不进仓库（底线）；热钱包只放少量资金，Amos 定期从冷钱包补充。第二版接 KMS |
| W2 | 签名怎么做 | 以太坊体系（ERC20、BSC）用开源库 **web3j 的签名部分**在本地签名；TRON 由节点构造交易、本地签名后广播 | 资金相关的签名用成熟的开源库，比自己写可靠；TRON 没有轻量的官方 Java 库，签名本身很简单（对交易 ID 做 secp256k1 签名），用公开测试数据核对 |
| W3 | 提现手续费 | 按原型：**ERC20 5、TRC20 1、BSC 0.5 USDT**，可在后台改（S16）；**从提现金额里扣**，实际到账 = 金额 − 手续费（和原型一致） | 现有系统没有收提现手续费；Amos 确认 |
| W4 | 热钱包余额不够时 | 不失败、不退款，提现停在"已审核待上链"，通知运维和风控补钱，补上后自动继续 | 余额不足是我们的问题，不该让客户的提现失败 |
| W5 | 拆成两步 | **S13a**：白名单、提交和限额、冻结、冷静期撤销、审核和驳回、大额延迟和紧急取消、退款，签名用替身；**S13b**：三条链真实签名广播、nonce 管理、确认和超时处理、热钱包检查 | 和 S12 一样，每一步都能单独停下确认 |

## 2. 规则
| 规则 | 做法 |
|---|---|
| 提交条件（AC-17） | KYC 已通过；只能提到白名单地址，**新地址 24 小时后生效**，最多 10 个；最小 10、单笔 ≤ 10,000、当日（UTC）累计 < 30,000 USDT（N-08）；金额不超过**可提金额**（余额 − 挂单冻结 − 持仓保证金 + 浮动亏损，浮动盈利不算，DF-02）。6 种拒绝原因各有错误码 |
| 冻结 | 提交时把提现金额从余额转到"提现冻结"（`WITHDRAW_FREEZE`），链上转出 金额 − 手续费，手续费归平台；退回时转回（`WITHDRAW_UNFREEZE`）；完成时从提现冻结扣掉（`WITHDRAW_PAYOUT`）。都走 `LedgerApi`，同一事务、幂等 |
| 冷静期（AC-18） | 2 小时，期间客户可以撤销，冻结立即退回；过了冷静期不能撤销，进入人工审核 |
| 审核 | 后台出金审核（页面和权限在 S16，S13 先做服务）：通过或驳回（驳回必须填原因，冻结退回）。每次操作记提现事件（谁、什么时候、做了什么） |
| 大额延迟（修复 F1，AC-21） | ≥ 3,000 USDT 审核通过后延迟 6 小时；期间后台可以紧急取消（资金退回，记事件和审计）。**延迟到期后直接生成上链任务**，不再依赖别的事件 |
| 上链（修复 F2，AC-19） | 三条链都支持。审核通过（大额是延迟到期）后写入任务表，5 分钟内广播 |
| nonce（修复 F6） | 以太坊体系每条链一个 nonce，启动时从链上同步，按顺序分配；广播被拒"nonce 太低"时重新同步。TRON 没有 nonce，交易 60 秒过期，过期没上链可以安全重建 |
| 防重复付钱（S13b） | 同一笔提现已经有"已发出"的广播记录，就不再用新 nonce 发；连不上节点时当作"可能已发出"，交给确认任务 |
| 节点拒绝（S13b） | 节点明确拒绝：记失败、以太坊体系重新同步 nonce，下次再试；同一笔连续 3 次被拒才失败退款（交易从没进过内存池，退款安全） |
| TRON 交易核对（S13b） | 节点构造的交易在签名前核对：交易 ID 是 raw_data_hex 的 SHA-256，并且里面是热钱包调 USDT 合约、转给这个地址这个金额；不一致就不签 |
| 超时（修复 F6） | 以太坊体系 30 分钟没确认：同一 nonce 提高手续费重发（最多 3 次）；仍不行通知运维人工处理，**不自动退款**（防止重复付钱）。只有能确定交易不会上链时（广播被直接拒绝、TRON 交易已过期且查不到）才失败退款（AC-20） |
| 完成 | 链上确认（ETH 12、BSC 15、TRON 19，同充值）后标为已完成，扣掉提现冻结 |
| 通知 | 每个状态变化推给客户（`/api/ws/trading` 的 `withdraw` 事件，和客户端约定一致）；站内信和邮件在 S15 |

## 6. 热钱包余额告警（v1.3，2026-10-17）
Amos 2026-10-17："余额告警现在就做"；同日补充："告警的默认下限让我可以设置，现在设置成零"。

```mermaid
flowchart LR
    T["每 5 分钟<br/>查已配置热钱包的余额"] --> M["内存里的最新余额"]
    C["后台 系统配置页<br/>6 个下限（默认 0）"] --> E{"下限 > 0<br/>且余额 < 下限？"}
    M --> E
    E -- 是 --> D["告警项 hot.链.usdt / hot.链.gas = DOWN<br/>告警邮件（30 分钟节流）"]
    E -- 否 --> U["UP（下限 0 时告警项不出现）"]
    M --> R["后台对账页<br/>显示余额、下限、最后查询时间"]
```

这张图想说明：余额一直在查、后台一直看得到；只有 Amos 在系统配置页填了大于 0 的下限，那一项才开始告警。

| 规则 | 做法 |
|---|---|
| 查什么 | 每 5 分钟（`falconx.wallet.hot-balance.interval`）查**已配置的**热钱包：以太坊体系（ERC20、BSC 共用 `FX_WALLET_ETH_HOT_ADDRESS`）用 `eth_call` 调 USDT 合约 `balanceOf`、`eth_getBalance` 查 ETH / BNB；TRON（`FX_WALLET_TRON_HOT_ADDRESS`）用 `/wallet/triggerconstantcontract` 调 `balanceOf`、`/wallet/getaccount` 查 TRX（没激活的账户余额为 0）。用现有的节点地址和 USDT 小数位（`usdt-decimals`）；ETH、BNB 18 位，TRX 6 位。只用地址，不需要私钥 |
| 只查配置了的 | 链配置了节点和 USDT 合约、并且配置了这一体系的热钱包地址才查；测试环境没配时什么都不查、什么都不显示 |
| 下限 | 后台"系统配置"页的 6 项（分组"热钱包余额告警"，权限 `config:edit`，**高危操作，必须填原因，写审计**）：`hotWallet.minUsdt.ERC20` / `.BSC` / `.TRC20`（USDT）、`hotWallet.minGas.ERC20`（ETH）/ `.BSC`（BNB）/ `.TRC20`（TRX）。**默认全部 0 = 不告警**（迁移 V25）。改了以后 5 秒内生效，不用等下一次查询。没有对应的环境变量（Amos 不用改服务器 `.env`） |
| 告警 | 下限大于 0 的项是一个 E8 告警项：`hot.ERC20.usdt`、`hot.ERC20.gas`、`hot.BSC.usdt`、`hot.BSC.gas`、`hot.TRC20.usdt`、`hot.TRC20.gas`。余额低于下限 → DOWN，走现有的告警邮件（`FX_ALERT_EMAILS`，异常、恢复各一封，同一项 30 分钟内不重复）。邮件说明里写：哪条链、哪种币、当前余额、下限（和配置键）、热钱包地址（地址是公开的，不是密钥）、查询时间。**这是业务告警**：只在后台域名的 `/api/health` 的 `alerts` 里出现，不进 `status`，不会让部署回滚（项目地图约定 24） |
| 下限改回 0 | 这一项的告警项立即消失；告警任务只清掉状态，不发"已恢复"邮件（`AlertMonitor`：不再出现的项清状态） |
| 查询失败 | 节点连不上、返回错误：**不算余额低**，只记日志（`热钱包余额查询失败`），保留上一次查到的结果（第一次就失败算正常）；节点问题由已有的 `node.<链>` 告警负责。后台显示"最近一次查询失败"和原因（不含节点地址） |
| 后台显示 | "资金 → 入金对账"页上方"热钱包余额"：每条链的 USDT 和手续费币一行，当前余额、告警下限（0 显示"不告警"）、状态（正常 / 低于下限 / 未启用告警 / 还没查到）、最后查询时间（`GET /api/admin/hot-wallets`，权限 `recon:view`） |
| 和提现的关系 | 不改提现逻辑：余额不够时提现仍停在"待上链"并通知风控（W4，`HOT_WALLET_LOW`，每条链每小时最多一次）。余额告警是提前提醒，让 Amos 在余额耗尽前补钱 |

**建议下限（Amos 在后台填，默认仍是 0）**：

| 项 | 建议 | 依据 |
|---|---|---|
| 每条链 USDT | 1,000 | Amos 给的建议值。注意单笔最多可提 10,000、当日累计 30,000，按实际日提现量调整（例如一天的提现量） |
| ETH（ERC20） | 0.02 | 代码里的 gas 上限 `gas-limit` = 100,000；发送前要求 ETH ≥ gas 价格 × 1.1 × 100,000。主网 gas 价格 5 gwei 时每笔约 0.00055 ETH，0.02 ETH 约 36 笔；10 gwei 时约 18 笔 |
| BNB（BSC） | 0.01 | 同一个 gas 上限；BSC gas 价格 1–3 gwei 时每笔 0.00011–0.00033 BNB，0.01 BNB 约 30–90 笔 |
| TRX（TRON） | 1,000 | 代码里的手续费上限 `tron-fee-limit-sun` = 30 TRX/笔，发送前要求 TRX ≥ 30，否则不发；没有质押能量时一笔 USDT 转账实际约 13–28 TRX（收款地址有没有 USDT 不同）。1,000 TRX 按上限算约 33 笔。原先建议的 100 TRX 只够 3 笔，低于 30 TRX 时提现就停 |

测试网的手续费币便宜，测试环境可以填小一些（例如 USDT 100、ETH 0.01、BNB 0.01、TRX 200）。

代码：`backend/src/main/java/com/falconx/lite/wallet/withdraw/HotBalanceMonitor.java`（查询、告警项、后台数据）、`HotBalanceProperties.java`（查询间隔）、`common/config/ConfigKey.java`（6 个下限）、`admin/ops/FundsOps.java`（后台接口）、`web/admin/src/pages/funds/HotWalletCard.tsx`（对账页卡片）。测试：`HotBalanceMonitorTest`（替身节点）、`HotBalanceMailTest`（邮件内容）、`AdminHotWalletTest`（后台设置、审计）、`AlertMonitorTest`、可选的真实节点核对 `HotBalanceRealNodeTest`（2026-10-17 实际查了 Sepolia、BSC 测试网、Nile 上的公开地址，格式对得上）。
